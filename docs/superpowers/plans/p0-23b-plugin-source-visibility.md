# 插件来源与库存可见性实施计划

> **致执行者：** 优先按任务顺序逐项落地，并在每个任务完成后做业务逻辑验证。步骤使用复选框 (`- [ ]`) 语法进行跟踪。

**目标：** 让用户区分并找到自己的插件、应用安装插件和官方市场条目。

**核心数据流：** 主进程分别读取当前 App 库存与用户插件根的受限元数据，经类型化摘要交给插件页；安装、启停、卸载仍只作用于当前 App 的 Grok Home。

**约束与边界：** 对应问题 1.4。用户要求展示自己的和 Grok 官方插件。扩展用户目录只读发现属于本计划待批准的边界变化；不改 `GROK_HOME`、不静默复制/链接插件、不继承用户信任、不执行插件来探测。

**主要风险：** 开发版/安装版库存被混淆；磁盘发现被误报为已启用；同名插件跨来源覆盖；合法空注册表回退导致卸载残留复活。

**技术栈：** Electron 主进程文件系统、现有 Grok 插件 CLI、Vue 3、Vitest。

**状态：** 目录元数据和代码核查完成，计划待批准；具体插件安装完整性未验证。

---

## 现状证据

2026-09-20 只读目录核查：用户 `~/.grok/installed-plugins` 有两个仓库目录，安装版 App Home 有一个，开发版 App Home 没有插件子目录且没有市场缓存。它们不是同一个库存。目录存在不等价于插件完整、已启用或已加载。

`listGrokPlugins` 只扫描当前 App Home。`PluginsPage` 失败时可能仍显示 0，市场 tab 不展示已安装列表错误；没有外部安装后的主动刷新入口。

## 任务 1：来源契约与只读发现

**文件：** `src/shared/runtime-plugin.ts`、`runtime-marketplace-plugin.ts`、`src/main/runtime/grok/grok-plugin-inventory.ts`、`grok-marketplace-inventory.ts` 及就近测试。

- [ ] 新增明确的来源与发现状态，区分应用已安装、用户目录发现、市场可安装。现有 `scope: user` 不能充当来源字段。
- [ ] 应用库存继续解析受限清单；用户目录仅发现固定插件根和受限清单字段，不读取配置、凭据、脚本全文或任意目录。
- [ ] 没有清单时仅显示目录名及“待识别”，不伪造 pluginId、版本、组件数；提供定位来源的受控入口。
- [ ] 跨来源以来源身份加插件身份区分，同名不覆盖；市场“已安装”必须对应当前应用的同源条目。
- [ ] 保持注册表权威性；缺失/损坏/合法空表/部分拒绝分别返回状态。未登记目录列为发现项，不默认启用。
- [ ] 仓库键与插件 ID 分开验证；只有合法路径及清单身份才能进入安装库存，保留真实路径边界、大小限制与拒绝原因摘要。
- [ ] 覆盖开发版空库存、用户目录缺失、符号链接越界、损坏清单、同名来源、卸载残留与部分无效注册表测试。

**完成标志：** 来源完整且不混淆，坏条目不阻断其他条目，也不扩大执行范围。

## 任务 2：插件页与管理操作

**文件：** `src/main/app-ipc.ts`、`src/main/index.ts`、`src/preload/desktop-api.ts`、共享 IPC、`PluginsPage.vue`、`plugins-page.ts` 及测试。

- [ ] 保留“已安装 / 市场”，已安装内显示来源分组；顶部数值区分加载中、失败、空与有效计数。
- [ ] 统一插件、MCP、技能三页的导航、搜索、列表密度、详情和空态，复用 P0-23C 的菜单/按钮视觉变量；本项负责问题 2.7 的能力页面范围，不改变 MCP/技能执行协议。
- [ ] 提供刷新入口，错误无论在哪个 tab 都可见；基本列表不等待所有详情请求成功才显示。
- [ ] 应用条目提供已有启停/卸载，用户发现条目禁用这些写操作并解释“尚未接入当前应用”，避免误删用户文件。
- [ ] 官方市场缺失时显示添加/刷新入口，使用现有 CLI 写 App Home；不靠目录 hash 或自报名称认定官方身份。
- [ ] 导入用户插件另经显式来源确认；优先复用已验证安装入口。无法确认本地自制插件安装契约时只展示，不假称已可用。
- [ ] 插件启用状态按配置/会话实际事实分别展示，运行中不得通过刷新或导入重启当前任务。

**完成标志：** 用户能找到所有已发现来源，并准确知道哪些插件能由当前 Runtime 使用；空列表有可执行的下一步。
